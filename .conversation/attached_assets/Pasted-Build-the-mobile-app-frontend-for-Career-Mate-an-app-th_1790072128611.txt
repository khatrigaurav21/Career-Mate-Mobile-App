Build the mobile app frontend for "Career Mate" — an app that evaluates job postings against a user's CV and generates tailored, downloadable CV/cover-letter PDFs.

## Scope: this is a frontend only. Do not build a backend.

A complete backend already exists, is already built, and is already deployed and running in production at `https://career-mate-api.onrender.com`. It owns the database, authentication, AI evaluation logic, and PDF generation. Your job is only the app the user taps around in — every piece of real data and every action goes through HTTP calls to that API.

Concretely, that means:
- Do not create your own database, ORM, or data models for jobs/profiles/evaluations. There is nowhere in this app to "add a table."
- Do not build your own auth system, password flow, or session handling beyond storing the bearer token this API gives you.
- Do not invent endpoints. Use exactly the ones listed below, exactly as shaped below. If a screen needs data this API doesn't provide, stop and flag it — don't fabricate a fallback endpoint.
- Make the API base URL a single configurable value (env var or config constant), not hardcoded inline in every file, since it needs to point at different backends across dev/staging/prod later.

## Tech stack

Build this as a real installable mobile app, not a website — the whole point is that it should feel native, not like a browser tab. Use Expo (React Native) so it runs on both iOS and Android from one codebase and is easy to preview live on a phone via Expo Go during development.

## Auth flow

Email + one-time code, no passwords anywhere.

1. `POST /auth/magic-link` — body `{ "email": string }` — response `{ "message": string }`. Triggers a 6-8 digit code sent to that email.
2. `POST /auth/verify` — body `{ "email": string, "code": string }` — response `{ "access_token": string, "refresh_token": string, "expires_in": number, "user_id": string, "email": string }`.
3. Store `access_token` securely (Expo SecureStore, not plain AsyncStorage). Every other request below sends it as `Authorization: Bearer <access_token>`.
4. A 401 response from any endpoint means the session expired — clear the stored token and route back to login.

## Profile setup flow

After login, check `GET /profile` (auth required). A 404 means this user has no profile yet — route them into first-time setup. Any other successful response means they're a returning user — go straight to the main app.

`GET /profile` success response: `{ "profile_id": string, "cv_markdown": string, "target_roles": string[] | null, "preferences": object | null }`

First-time setup needs three ways to build a profile, presented as real, equally-weighted options (not one primary path with two buried alternatives):

1. **Upload a resume file** — `POST /profile/upload`, multipart form, file field name `resume_file`. Accepts PDF, DOCX, or plain text, max 5MB. Success: `{ "profile_id": string, "cv_markdown": string }`. On a 422 response, the body includes `"fallback": "paste_text"` — show the user a message suggesting they paste their CV as text instead, and offer that option directly.
2. **Paste CV text** — `POST /profile/paste`, body `{ "cv_markdown": string }` (plain text or markdown, used as-is). Same success shape as above.
3. **Guided Q&A** — a short form (name, current role, years of experience, a few work history entries with company/title/dates/achievements, education, skills, proof points, target roles, location/salary/avoid preferences) that gets assembled into an `answers` object and sent to `POST /profile/intake`, body `{ "answers": { ...all of the above... } }`. This call can take up to 60 seconds (it's writing the CV with an LLM) — show a real loading state, not a spinner that looks stuck.

All three return the same `cv_markdown`/`profile_id` shape. After any of them succeeds, the user is done with setup — take them to the main pipeline screen.

There should also be a way to redo profile setup later (e.g. from a settings/profile screen), not just once at signup — a user's CV changes over time.

## Main flow: the job pipeline

`GET /pipeline` (auth required) — response `{ "jobs": [{ "job_id": string, "company": string | null, "title": string | null, "score": number | null, "status": string }] }`. This is the home screen: a list of every job the user has evaluated, each showing title, company, and a visually distinct score indicator (score is 0-5; null means still processing or something went wrong — handle that state, don't just show blank). Empty list is a real first-use state — design a proper empty state, not a blank screen.

From here, the user starts a new evaluation. Give them three real, equally-weighted ways to submit a job, matching the profile-setup pattern above — this is a deliberate product decision, not an afterthought:

**`POST /evaluate`** (auth required), one of:
- `{ "job_url": string }` — a link to the posting; the backend fetches and reads it.
- `{ "job_description": string }` — pasted job text.
- multipart form, file field name `job_file` — an uploaded PDF/DOCX/text document containing the JD.

This call can legitimately take up to 90-150 seconds (URL fetching + AI evaluation) — show a real progress/loading state with reassuring copy, not a raw spinner. A 422 response may include `"fallback": "paste_text"` — same pattern as profile upload: suggest pasting text instead.

Success response: `{ "job_id": string, "score": number, "report": { "A": string, ..., "G": string, "H"?: string } }`. On success, navigate to that job's detail screen.
